# Design: serve-speech-cooldown-tuning

## Context

**Router settings today** (`litellm/config.base.yaml`, LiteLLM 1.81.9 pinned):

| Setting | Value |
|---|---|
| `num_retries` | 2 |
| `retry_after` | 3 |
| `allowed_fails` | 3 |
| `cooldown_time` | 20 |
| `allowed_fails_policy` | `RateLimitErrorAllowedFails: 1000000` |

The `allowed_fails_policy` line is what makes LiteLLM use count-based cooldowns instead of its "cool on the first 429 if a sibling exists" heuristic. Together these satisfy `gpu-inference-availability`'s "Proxy cooldown is reserved for unavailable deployments": busy never cools a deployment, and a cooldown needs three connection-level or 503 failures and lasts at most 30 s.

**The speech groups** (`gpu-server/models.yaml`):

| Group | Deployment | Timeout | RPM |
|---|---|---|---|
| `heartcode-stt` | one: Pea `:8200` → the speech meter → faster-whisper | 180 s | 60 |
| `heartcode-tts` | one: Pea `:8201` → Kokoro | 180 s | 60 |

**How HeartCode uses them.** STT always goes through LiteLLM. Live TTS goes to Pea's direct gateway by default (`SPEECH_LIVE_ROUTE=direct`), and through LiteLLM only on the `litellm` trial route; voice previews also use LiteLLM.

HeartCode's admission limiter keeps in-flight speech at 4/4 and refuses the excess as busy. It retries transient statuses (429, 502, 503, 504, connect errors) itself, as follows:

| Retry setting | Value |
|---|---|
| Retries | 2 |
| Backoff | full jitter, base 0.25 s, cap 1.0 s |
| Total added wait | at most `SPEECH_RETRY_DEADLINE_SECONDS` = 2.0 |
| `Retry-After` | honoured, or the turn reports busy at once if it would overrun |

## Goals / Non-Goals

**Goals**

- An error from a sole speech deployment reaches the caller as that error. It never becomes a window in which every request is refused without being tried.
- Any retry LiteLLM adds for speech is immediate and single, so it cannot exceed the caller's 2-second budget.
- Chat groups are untouched.

**Non-Goals**

- RPM caps, the `heartcode-tts-128k` route, and capacity (see the proposal).

## Decisions

### 1. Fix cooldown per speech group, not globally

Chat groups still benefit from cooldown, because a broken replica should be routed around while its siblings serve. So the global `allowed_fails` / `cooldown_time` stay.

**The speech groups opt out** with a per-deployment setting in their manifest `params`, which the generator copies into `litellm_params`.

**Candidates, in order of preference:**
- **(a) `cooldown_time: 0` on the deployment.** LiteLLM reads a per-deployment `cooldown_time` from `litellm_params`, and 0 means "do not cool down".
- **(b) The router's own single-deployment rule, if the pinned version has one.** Some LiteLLM releases skip cooldown when a group has only one deployment. That would make (a) belt-and-braces rather than necessary.
- **(c) A group-scoped `allowed_fails_policy` / `model_group_retry_policy` in `config.base.yaml`.** This is the fallback if neither of the above holds on 1.81.9.

**Which one ships is decided by test, not by documentation.** Task 1 runs the pinned image against the fake backend in `tests/integration/` with a single-deployment group, returns 500 three times, and checks that the fourth request still reaches the backend.

### 2. Fail fast: one immediate retry at most

HeartCode's budget is 2 s and it does its own jittered retries. A LiteLLM retry that waits `retry_after: 3` therefore always arrives after HeartCode has given up. It holds the deployment's only slot for nothing and stacks a second retry layer under the caller's.

**For the speech groups:**
- `num_retries: 1` with no fixed delay, if the pinned version supports a per-group or per-deployment retry count and delay;
- otherwise `num_retries: 0`, leaving retries to the caller, which already does them correctly.

**Either way the caller's policy is the only one that sleeps.** Retrying a sole deployment immediately mostly helps a connection reset. It cannot help a busy host, and HeartCode's limiter keeps the host from being over-asked.

### 3. Source, regenerate, restart

The values go in `gpu-server/models.yaml`, plus `config.base.yaml` only for option (c). `config.yaml` is regenerated by `render-config.py`; `validate_config.py` and the CI config check pass.

The change is applied on elm with `docker compose restart litellm`: the bind-mounted config does not reload on `up -d`. Then it is verified with `/v1/model/info` under the master key, which shows the speech deployments' effective `litellm_params`.

## Risks / Trade-offs

- **A dead speech backend is retried on every request instead of being skipped for 20 s.** With one deployment, "skipping" meant refusing anyway. The real cost is that each request now pays a connection attempt; at 180 s timeouts that could be long. *Mitigation:* a dead backend usually fails its connection quickly. HeartCode bounds its own wait (2 s added, plus its request timeout), and Pea's monitoring alerts on a group with no completions for an hour (`gpu-inference-availability`).
- **Behaviour differs across LiteLLM versions.** *Mitigation:* the integration test pins the behaviour, so an image bump that changes it fails CI rather than production.
- **Overlap with the trial companion.** Both touch the speech entries' `params`. *Mitigation:* each names the other in its proposal, and whichever lands second rebases.
