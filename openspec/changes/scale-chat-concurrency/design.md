# Design: scale-chat-concurrency

## Context

Measured on `heartcode-gpu4` 2026-09-16: ~32 tok/s decode, ~123 tok/s prompt processing, single slot, 16K context, Q8 KV (~1 GiB), llama-server at 6.4 GiB. `N_CTX` is the total context split across slots. Host CPU is a 2-core Celeron, so batch sizes are small (128) and prompt processing is the bottleneck for TTFT. The earlier load-test era ran two slots per GPU on 6 GiB cards. LiteLLM supports a Redis-backed scheduler with `priority`, and routing is least-busy with no session awareness. Rediska's dimension agents share a large profile prefix but put dimension-specific system prompts first, defeating `--cache-reuse`.

## Decisions

1. **Qualify slots empirically, per model group.** Start with `MAX_CONCURRENT_REQUESTS=2`, `N_CTX=16384` (8K per slot) on one NSFW replica; k6 mixed-load scenario reports aggregate tok/s, p95 TTFT, per-stream decode. Success criteria are in the spec. Only then fleet-wide.
2. **Affinity via a session header.** Consumers send `X-Session-Id`; a small routing layer (LiteLLM `custom_routing_strategy` keyed on a Redis `session→deployment` map with TTL, falling back to least-busy) pins the session; the wrapper forwards `id_slot` derived from a per-replica session→slot map. *Rejected:* client-side pinning to a replica URL — bypasses the proxy's auth and limits.
3. **Priority via LiteLLM scheduler**: enable Redis for the router, set `priority` per key (interactive 0, batch 1). Batch requests wait in the scheduler rather than at the backend.
4. **Prompt layout guidance for batch consumers**: shared prefix first, task-specific instruction last, so sequential calls on one slot reuse the cache. Documented in the client contract.
5. **Capacity table** generated by the load-test analysis script from k6 output and committed to `docs/load-test-findings.md`.

## Risks / Trade-offs

- [Per-slot context halves] → SFW's 16K requirement means SFW may stay single-slot; qualify NSFW first.
- [Prompt-heavy requests stall co-batched streams on Pascal] → TTFT bound in the gate; consider `--parallel 2` only.
- [Affinity concentrates load] → affinity only within cache lifetime (TTL ≈ minutes) and never overrides an unhealthy deployment.
- [Redis dependency for the router] → already available on Prod; failure falls back to least-busy without priorities.

## Migration Plan

Qualify on one replica → fleet env change with rolling restart → router Redis + priorities → affinity layer. Each step independently reversible.

## Open Questions

- Whether llama.cpp's slot-level prompt cache survives `--cont-batching` slot reassignment well enough to justify `id_slot` pinning, or replica-level affinity is enough.
